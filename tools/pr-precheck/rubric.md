# Rubric: is this pull request ready to submit?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diff matches plan | The diff's changed files and hunks, read against the plan's stated scope (the in-scope files and approach), its not-in-scope lines, and its deviation notes or stated deferrals. | Every changed file and hunk falls inside what the plan names or inside a deviation note that announces it, and every planned deliverable is present in the diff or is explicitly deferred in the plan's own scope note, a deviation note, or the description. A one-line fix plus a test the plan lists is a pass. Fails when a hunk does work the plan never named or scoped out (a new option, a rewrite of an adjacent function, a rename pass, a file the plan never touches), or when a planned deliverable is missing with no note anywhere, no matter how good the extra or remaining work is. An honestly disclosed deferral is a pass, not a fail: "less than everything" holds the package only when the shortfall is silent. | required |
| Description matches diff | Each factual claim in the PR description about what changed ("implements the plan exactly", "no changes outside X", "docs now document Y", "adds a test for Z"), read against the diff's actual hunks and files. | Every claim of fidelity or coverage is true of the diff: what the description says was changed is in the diff, and nothing it calls out of scope appears in it. Fails when the description claims more than the diff delivers (a promised docs update or test that is absent) or asserts fidelity the diff contradicts ("no other changes" over an extra hunk). A terse description that makes no false claim passes. | required |
| Test evidence decisive | The PR's test-evidence section, read against the plan's test plan and the reproduction's own steps, plus the outcome of the repo's own checks (test suite, linter, build) as the evidence shows them. | The evidence re-runs the plan's own repro or named test-plan scenario against the changed code and shows an observable before and after (a value, output, exit code, or transcript that differs and matches the plan's stated expected-after), on the path the fix actually changes, and shows the outcome of the repo's own stated checks or the new test. Every failure mode the plan's test plan names is covered, or the uncovered one is explicitly deferred. Fails when the evidence is a bare assertion ("tested locally", "works on my machine", "tests pass" with no test named), exercises a control or unchanged path instead of the fixed one, re-runs only part of what the plan's test plan named with no deferral, or shows no outcome for the repo's checks. A terse transcript that meets this passes. | required |
| Diff reviewable | The unified diff and the commit list: the hunks themselves, not the description. | The change is visible and nothing rides along that a reviewer must discard: no debug prints or leftover logging, no commented-out code, no dead or unused functions or imports, no TODO notes added for later, no whitespace-only or reformatting hunks, no unrelated drive-by edits. Mechanical churn still counts as debris, even around a correct fix. Fails when any such debris appears in the diff. Commit message style never decides this check. | required |
| Template and policy honored | The repo-facts block's stated PR-template asks (live: the repo's PR template and CONTRIBUTING.md), read against the PR description and diff: each ask, and each artifact the template says the PR must carry (an issue-closing line, a changelog or whatsnew entry, tests, type annotations, a checklist). | Every stated template ask is answered with real content in the description, or is visibly satisfied in the diff (a required changelog entry appears as a changed file), or is stated as not applicable with a reason. Fails when a required section or artifact is blank, boilerplate, or absent: an unfilled checklist, a missing issue-closing line, a missing changelog entry the template names. A repo with no stated template asks passes this check. | required |
| AI disclosure present | The repo-facts block's contribution policy line on AI use (live: CONTRIBUTING.md and the template), read against the description's own words. | When the stated policy requires disclosing AI assistance, the description contains a disclosure in its own words naming that AI helped (and, where the policy asks, how). Treat the PR as AI-assisted work. When the policy is silent or states no requirement, no disclosure is needed and the check passes. Fails when a stated disclosure requirement is unmet. | required |
| Maintainer direction engaged | The thread highlights' explicit maintainer-stated direction (an owner or member naming a cause, a preferred approach, an unanswered question to the author), read against the description and diff. | When the thread carries an explicit maintainer direction or question, the PR follows it, or the description engages it and gives a reason for departing. A thread with no explicit maintainer direction passes. Fails when the diff or description ignores or contradicts such a direction without engaging it. | required |
| Commits legible | The commit list's messages, read against the diff. | Each message says what the commit changes. Never changes the verdict; note it in the summary as a quality signal. | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. A single required
check graded `fail` or `unclear` rejects the package: `unclear` counts
as `fail`, because a PR whose fidelity, evidence, cleanliness, or
compliance cannot be verified from the package is not ready to submit.
`preferred` checks never change the verdict; they only add a quality
note to the summary. A PR that honestly discloses a shortfall can be
ready: a disclosed deferral never fails a check by itself.
