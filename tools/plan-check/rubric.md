# Rubric: is this plan ready to post and build from?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Diagnosis grounded | The candidate plan's stated cause (however it is labelled — "Diagnosis," "Cause," or an unlabelled opening paragraph), read against the repro evidence block's own steps, control runs, and artifacts — never against what the thread merely guesses or assumes the cause to be. | The stated cause is consistent with every control run and artifact the repro evidence shows, and no control's actual result rules it out. The cause is allowed to explain a supporting control with a plausible mechanism the repro evidence does not spell out in those words (a diagnosis is an inference, not a transcript) — that kind of plausible reading of a control that fits the stated cause is a pass, not a gap. Fails only when a control's actual result actively points to a different mechanism, isolates a variable the stated cause does not touch, or shows the claimed defect already absent before the claimed cause could act — even when the diagnosis matches a cause the thread already floated, since a thread's own guess can be wrong and adopting it does not ground a diagnosis the repro evidence itself contradicts. | required |
| Scope bounded | The candidate plan's stated in-scope/not-in-scope lines and the files or areas it names, read against the issue's actual reported behavior and expected fix — not against other opportunities the surrounding code happens to present. | The proposed change is one coherent fix for exactly the issue's reported behavior. A stated not-in-scope line (or the plain absence of any add-on) keeps out refactors, migrations, version bumps, new options/props, or redesigns the issue never asked for. Deferring adjacent work explicitly, with a stated reason, is a pass, not a fail. Fails when the proposed changes reach beyond what fixes the reported behavior — including a correct core fix bundled with "while I'm in there" work — no matter how well-reasoned the extra work sounds. | required |
| Executable | The candidate plan's stated approach: the files or areas it names and the concrete first action, read for whether every decision needed to start work has actually been made. | A stranger could begin without asking the author anything: at least one specific file, function, or area is named, and the first concrete action is stated as a decision, not a question. Every choice the work depends on (which layer, which library, which of two approaches) is made in the plan itself. Fails when the "approach" is actually an open-ended research task ("investigate," "profile and see," "not sure which layer"), when no file or area is named at all, or when a real decision is explicitly deferred to build time ("upstream or vendored, whichever is easier"). | required |
| Test plan decisive | The candidate plan's stated test plan, read against the repro evidence block's own steps, artifacts, and control runs. | Names an observable result tied specifically to this fix: a re-run of the repro's own steps (or an equivalent concrete check) with a stated expected outcome — an exit code, specific output, a value that must change, a control that must stay unchanged. Fails when the test plan names only a general activity with no fix-specific observable outcome ("should feel fast," "shouldn't feel broken," "run the full test suite and make sure nothing regresses") — this fails even when the rest of the plan is sound, because nobody reading only the test plan could tell whether this fix worked. | required |
| Honest about unknowns | The plan's own stated risks, open questions, or deferred items, read against its confidence language elsewhere in the same plan. | An unknown the repro evidence does not settle (an untested platform, an unverified tool, a cost not yet measured) is named as open rather than asserted as settled fact. A deferred question is stated as deferred, with what would resolve it, not smuggled in as certainty. Never changes the verdict; note it in the summary as a quality signal. | preferred |
| Comms respect thread and repo | The candidate plan comment's own wording, read against the thread highlights' explicit maintainer-stated direction (an owner or member naming a cause, a preferred approach, or an approach they already rejected) and against the repo-facts block's contribution/AI-policy line. | When the thread carries an explicit maintainer-stated direction or cause, the comment engages it — follows it, or gives an evidence-backed reason for departing from it — rather than proceeding as if the thread said nothing. When the repo's stated policy requires disclosing AI assistance, the comment names the tool and the extent of its use; when the policy is silent, or only conditions AI use without requiring disclosure, no disclosure statement is needed to pass. Fails when the comment's plan ignores or contradicts an explicit maintainer direction present in the thread without engaging it, or when the repo's stated AI policy requires disclosure and the comment gives none. A thread with no explicit maintainer direction, or a repo with no stated AI-disclosure requirement, passes this check by default. | required |

## Verdict rule

Accept only if every `required` check grades `pass`. A single required
check graded `fail` or `unclear` rejects the package: `unclear` is
treated as `fail`, because a plan whose grounding, scope, executability,
test plan, or comms cannot be verified from the package is not ready to
post and build from. `preferred` checks never change the verdict; they
only add a quality note to the summary.
