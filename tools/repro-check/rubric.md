# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| Environment recorded | The repro report's environment statement, read against the issue's stated target version (or the repo-facts "latest release" line when the issue names none) and any other variable the issue's trigger depends on (OS/platform, browser, driver, install method, dependency version). | The environment line names the tool/library version, platform, and every other variable the issue's trigger depends on — enough that a stranger could place the exact conditions of the attempt. If the tested version or platform differs from what the issue targets, the report says so in its own words rather than presenting an older or different setup's result as if it were current. Fails when there is no environment statement at all, when a variable the trigger depends on is missing, or when a deviation from the issue's target is left unstated. | required |
| Steps followable | The repro report's steps, read against the issue's own reproduction steps or trigger description to see whether the same trigger is used and whether a stranger could run them. | A stranger with the stated environment could execute the steps as written: a defined starting point (files, config, or input shown or attached in the report itself) leading to the specific action the issue names as the trigger. Fails when a needed input, config, or repository lives only in the reporter's private setup and is not shared in the report, when a step a stranger would have to guess is missing, or when the sequence never reaches the issue's actual trigger. | required |
| Behavior shown matches the issue | The artifact inside the repro report (command output, log excerpt, error, or described screen state) plus its "Expected"/"Actual" lines, read against the Issue section's own excerpt of the current and expected behavior. | The artifact shows the same failure mode or the same present-vs-absent behavior the issue names, produced by following the issue's actual trigger (not a different flag, syntax, or input). An honest "could not reproduce" is a pass too, provided the attempt used the real trigger and the report names what was tried and what differed. Fails when the artifact shows an adjacent symptom (a different error class, a different exit behavior, the program still running when a crash was claimed) instead of the issue's own behavior, when the steps used a different trigger than the issue's, or when an untargeted version's behavior is presented as if it confirmed the issue without acknowledging the version gap. | required |
| Honesty of the claim | The repro report's own concluding language (its "Actual"/"Analysis"/summary lines) and the claim comment's stated certainty, read against the artifact the "Behavior shown" check found. | The stated conclusion claims no more than the artifact supports: words like "confirmed," "guaranteed," or "proves" appear only when the artifact itself carries that certainty on the issue's real trigger, and nothing is generalized to a platform, release, or scenario that was never actually tested. A cannot-reproduce result is stated as exactly that. Fails when the conclusion overclaims relative to what was shown — reframing a different result as confirmation, generalizing beyond what was tested, or asserting certainty from repeating the same run rather than from new evidence. | required |
| Comms respect the repo | The claim comment's and repro report's own wording, read against the repo-facts block's "bug reports" template line and "contribution policy" line (including any named AI-policy file). | Both comments are specific to this issue — they could not be pasted unchanged onto a different one — and promise only what the poster can keep (no guaranteed fix timelines, no reserving the issue by tone alone); the repro report answers what the repo's stated template asks. When the contribution/AI policy requires disclosing AI assistance, the comments name the tool and the extent of its use; when the policy is silent, or merely conditions AI use without requiring disclosure, no disclosure statement is required to pass. Fails when a comment is interchangeable boilerplate, promises an outcome or timeline it cannot back, or when the repo's policy requires AI disclosure and the comments give none. | required |
| Next step named | The claim comment's stated next action. | Names a concrete next investigative step tied to this issue's specifics (a file, function, or hypothesis to check next) rather than a generic "will report back" or silence. | preferred |

## Verdict rule

Accept only if every `required` check grades `pass`. A single required
check graded `fail` or `unclear` rejects the package: `unclear` is
treated as `fail`, because proof that cannot be verified from the
package is proof that is not ready to post. `preferred` checks never
change the verdict; they only note a nice-to-have in the summary.
